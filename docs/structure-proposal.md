# Threads運用 構成案(RADIODJ)

参照した投稿(karasu.claude / Threads運用ツリー)を批判的に検討し、
「Claude Code で実際に回る形」に再設計したもの。

---

## 0. 前提:今の状態

このリポジトリには `README.md` しかない。
つまり今足りないのは **フォルダではなく、蓄積されたデータと1本のループ**。

元投稿のツリーは 7大分類 / 約38フォルダ。
これは「投稿として伸びる形」であって「毎日運用する形」ではない。
フォルダを作るコストは 0 だが、維持するコスト(毎回どこに入れるか判断する)は毎日かかる。

---

## 1. 元投稿の各項目を「必要 / 不要」で判定

各項目について、**一度「不要」側の論を立ててから**結論を出す。

### アカウント設計(発信ジャンル/ターゲット/プロフィール/専門知識/ポジション/収益化の流れ)

- 不要論:6フォルダは過剰。これは1回書いて終わる静的情報で、更新頻度がほぼゼロ。
  分割すると全部が中途半端に埋まって腐る。
- 必要論:Claude に書かせると、この前提が無い限り毎回「一般論のAI記事」が出てくる。
  最も再利用される情報でありながら、最も参照されない場所に置かれている。
- **結論:必要。ただしフォルダではなく `CLAUDE.md` 1ファイル。**
  Claude Code は `CLAUDE.md` を毎セッション自動で読む。ここに置いて初めて「設計」が効く。
  フォルダに置いた設計書は、誰も(Claude も)読まない。

### ネタ探し(競合アカウント調査/伸びた投稿/トレンド/よくある質問/投稿ネタ一覧)

- 不要論:4つとも「ネタの供給源」でしかない。分けた瞬間、ネタを思いついたときに
  「どこに入れるか」で手が止まる。実際に毎日開くのは「投稿ネタ一覧」だけ。
- 必要論:「競合の伸びた投稿の実物」だけは別種。これは自分の勝ちパターンを検証する
  対照群であり、ネタではなく証拠。
- **結論:`ideas.md`(ネタ1本)+ `swipe.md`(実物の保存)の2ファイルに集約。**
  トレンド・よくある質問は ideas.md の1行として入れれば足りる。

### 投稿作成(冒頭フック集 ほか)

- 不要論:「作成」は作業であって保管対象ではない。フォルダにしても何も溜まらない。
- 必要論:フック集は実データとして価値がある(どの型が伸びたかを後で照合するため)。
- **結論:作業は `.claude/commands/draft.md`(コマンド)、
  フック集は `references/hooks.md`(参照データ)。フォルダは要らない。**

### 投稿管理(下書き/投稿済み/投稿予定/再利用候補/シリーズ企画)

- 不要論:5つのうち3つは「状態」。状態をフォルダで表すと、同じ投稿が複数箇所に存在し、
  どれが正か分からなくなる。「再利用候補」に入れた投稿は「投稿済み」でもあるはず。
- 必要論:下書きと投稿済みの区別だけは物理的に要る。作業中のものが見えないと止まる。
- **結論:一方向で不可逆な遷移(下書き→投稿済み)だけフォルダ移動。
  可逆・多重に付く属性(再利用候補・シリーズ・テーマ)は frontmatter のメタデータ。**
  → `posts/drafts/` と `posts/posted/` の2つだけ。再利用候補・シリーズ企画は削除。

### 分析・改善(投稿データ/伸びた理由/伸びなかった理由/勝ちパターン/改善メモ)

- 不要論:後ろ4つは全部「投稿データ」1つから導かれる派生物。手で書いた瞬間、
  それはデータではなく後知恵の感想文になる。4フォルダ分の文章を書く時間で3投稿できる。
- 必要論:ここが唯一、複利で効く場所。ただし人が書くのではなく、データから生成させる。
- **結論:`data/metrics.csv`(生の数字1本)+ `insights.md`(そこから導出、コマンドが更新)。**
  「伸びた理由/伸びなかった理由/勝ちパターン」の3分割は不要。同じ1つの分析の3つの断面。

### 集客・収益化(固定投稿/LINE・メルマガ導線/アフィリエイト/自社商品/販売導線)

- 必要論:出口が決まっていないと投稿の内容がブレる。何のために書くかは最初に要る。
- 不要論(こちらが強い):フォロワーもデータもない段階で販売導線を5フォルダ用意するのは、
  走る前に靴を10足並べる行為。空フォルダは「やってる感」だけを生む。
- **結論:今は不要。`CLAUDE.md` に「出口は◯◯」の2行だけ書く。**
  実際に売るものができた時点でフォルダを作る。

### 自動化(ネタ収集/投稿作成/投稿チェック/投稿分析/プロンプト集/作業マニュアル)

- **ここが元投稿の最大の欠陥。**
  Claude Code において自動化とは `.claude/commands/`・`.claude/skills/`・`CLAUDE.md` のこと。
  「自動化」という名前のただのフォルダにプロンプトを置いても、Claude は読まない。
  読まれないプロンプト集は、自動化ではなくメモ帳。
- **結論:フォルダとしては不要、仕組みとしては必須。
  `.claude/commands/*.md` に移す。作業マニュアルは `CLAUDE.md` に統合。**

## 2. 元投稿に「そもそも無い」もの(= 本当に足りないもの)

構造を整える以前に、これが無いと分析フォルダは全部ポエムになる。

1. **投稿ID** — 投稿と数字を紐づける一意のキー。これが無いと
   「どのフックが伸びたか」は永久に分からない。
2. **投稿前の仮説** — 「なぜこれが伸びると思うか」を投稿前に書く欄。
   事後に書く「伸びた理由」は100%後知恵で、次の判断に使えない。
3. **計測タイミングの固定** — 投稿24時間後、など。直後の数字と3日後の数字を
   混ぜて記録すると、比較不能になり全データが無価値になる。
4. **文体ルール / NGワード** — これが無いと Claude の出力は毎回
   「〜してみませんか?」の一般論に寄り、毎回手直しが発生する。
5. **却下の記録** — 落とした案と理由。無いと同じダメ案を何度も生成させることになる。
6. **1日のループの定義** — 構造があってもループが無ければ動かない。

## 3. 構成案

```
RADIODJ/
├── CLAUDE.md                  # アカウント設計 / 文体ルール / NG / 運用ループ(毎回自動読込)
├── insights.md                # データから導いた勝ちパターン。/review が更新する
├── .claude/
│   └── commands/
│       ├── idea.md            # ネタ出し → ideas.md に追記
│       ├── draft.md           # ネタ → 下書き生成(frontmatter付き)
│       ├── check.md           # 投稿前チェック(NG・フック・長さ・CTA・仮説の有無)
│       └── review.md          # metrics.csv を読んで insights.md を更新
├── data/
│   ├── ideas.md               # ネタ一覧(status: todo / drafted / posted / dropped)
│   ├── metrics.csv            # 投稿ごとの実測値(唯一の生データ)
│   └── swipe.md               # 競合・自分の伸びた投稿の実物
├── references/
│   └── hooks.md               # 冒頭フック型の一覧と実例
└── posts/
    ├── drafts/                # 生成された下書き
    └── posted/                # 投稿したら移動(IDは変えない)
```

**4フォルダ / 8ファイル。**元投稿の38フォルダに対して約1/5。
毎日開くのは `ideas.md` / `posts/drafts/` / `metrics.csv` の3つだけ。

### 下書きの frontmatter(固定スキーマ)

```yaml
---
id: 2026-09-01-a
theme: claude-code
hook: 逆説            # 逆説 / 数字 / 失敗談 / 断言 / 質問
cta: profile          # none / profile / reply
hypothesis: 「Claude Codeは難しい」の逆を張ると初心者が反応するはず
---
```

`hypothesis` が最重要。これがあると `/review` のとき
「仮説が当たった/外れた」で判定でき、次の投稿に反映できる。

### metrics.csv の列(固定)

```csv
id,posted_at,hook,theme,cta,views,likes,replies,reposts,follows_delta,measured_at
```

`measured_at` は必ず投稿から同じ時間後(例:24時間後)に揃える。
ここを揃えないと、全データが比較不能になる。

### 運用ループ

| タイミング | やること |
|---|---|
| 朝 | `/review` — 前日投稿の数字を metrics.csv に入れ、insights.md を更新 |
| 昼 | `/idea` → `/draft` → `/check` → 投稿 → posts/posted/ に移動 |
| 週1 | insights.md を読み、確度が上がった知見を CLAUDE.md に昇格させる |

`insights.md` → `CLAUDE.md` への昇格が、この構成の学習部分。
検証済みの勝ちパターンだけが常時読み込まれる場所に上がっていく。

## 4. 最初にやること

分析の仕組みを先に作っても、データが無ければ何も出ない。
**20投稿ぶんの metrics が溜まるまで、「勝ちパターン」は統計的に意味がない。**

だから最初の2週間に必要なのは2つだけ:

1. `CLAUDE.md` を書く(アカウント設計 + 文体ルール)
2. 毎回同じ形式で投稿し、同じタイミングで数字を記録する

`.claude/commands/` の整備も insights.md も、データが溜まってからで遅くない。
先に38個のフォルダを作ると、埋まらない空フォルダを眺めて満足して終わる。
